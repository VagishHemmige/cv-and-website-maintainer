# Save verification and later status

Valid numeric dates with unpadded month/day components now produce a review warning, including teaching session dates. The suggestion preserves year/month/day precision; null, present and already padded values are unchanged. Invalid calendar dates or incompatible precision still produce their existing errors, without a misleading formatting-only suggestion. The validator never rewrites source dates. Text-sorting CV consumers can misorder unpadded dates; inspect the actual consumer and obtain exact proposal approval for formatting corrections.

New YAML saves require linked [approval evidence](approval-evidence.md): the actual response/context, available message time, exact candidate ID/hash and destination. The helper persists a verified private copy before writing and records its hash in the attempt and completion receipt. Recovery rechecks that copy without rewriting records. Older completed receipts are preserved and missing evidence is reported separately as not_recorded; an interrupted legacy save without linked evidence requires reviewed reconciliation, never fabricated backfill. Evidence is an audit trail, not independent human authentication.

Before an apply or recovery completion receipt, compare the expected post-save YAML snapshot: the target's approved candidate bytes, every other tracked YAML file and optional media file layout. Repeat the comparison after validation. Recheck current profile scope before issuing the receipt. Detect changed staged bytes before any live write. These checks narrow avoidable verification gaps; they do not lock other editors or promise an atomic multi-file transaction.

The configured bibliography remains read-only. An auto-export alone no longer invalidates YAML approval. Before writing, validate a disposable copy of the exact approved YAML against the current bibliography; preserve the original staged bibliography as proposal evidence. After writing, validate the live records again. Check the bibliography hash before and after validation, retrying at most three times if an export changes it. New or changed record errors and all parser/structure failures stop the operation. Only the exact pre-existing record errors explicitly reviewed in the proposal may remain; compare their structured identities at every validation gate. Compare the complete set of WARNING lines with the proposed validation shown for approval. Any added or removed warning requires renewed review: show the previously reviewed and current warnings, prepare a fresh proposal and obtain exact approval before a write. Do not silently accept warnings just because validation exits successfully.

Each new completion receipt records validated_bibliography_sha256, the generation used for successful validation. Status compares against that hash; older receipts without it retain their original proposal hash. A later export is reported as snapshot drift while preserving historical evidence. The receipt describes the successfully validated snapshot, not a lock on future exports. Bibliography configuration changes still require reconciliation, and all YAML stale-source, scope, backup and tamper checks remain in force.

On failure after a target write, report the actual outcome through status and preserve the backup. A matching target without a completion receipt is saved_unverified, not an untouched file. A conflicting target needs review. Do not automatically retry, roll back or erase evidence. Changed warnings, new/changed record errors, parser/structure failures or an export that never stabilizes can prevent verification even though the requested YAML bytes were saved. Show the validation differences and a recovery proposal; do not claim another approval alone makes them safe. Recovery revalidates without rewriting records and cannot issue a receipt while warnings differ from the reviewed proposal. Unresolved differences need explicit reconciliation, not a blind apply retry.

The status command retains its target-oriented status for compatibility and also returns:

- historical_save_verified: a prior completion receipt exists and is not contradicted by a recorded failed-before-write recovery history; this is historical evidence, not a fresh validation run.
- write_attribution: verified_receipt, confirmed_target_write, known_failed_before_write, unconfirmed, legacy_recovery_unattributed, or contradictory_recovery_history. Read it separately from current file hashes.
- current_snapshot_matches: current files match that proposal's expected post-save snapshot, including optional file layout and bibliography.
- changed_files: names of differences, with markers for layout or bibliography configuration changes.
- target_currently_approved: whether the current private profile still allows this target.

For a proposal awaiting approval, current_snapshot_matches will normally be false because the approved candidate has not been applied. That is not a corruption finding. Later legitimate edits or exports can also make an older snapshot differ. Preserve the historical receipt and explain the subsequent change; never treat every older differing snapshot as a failed historical save. Read list output's history/snapshot details alongside its status. Linked pending items expose these details too.

A target that differs from its verified saved bytes is changed_after_save ("changed after verified save"), including a missing target or a return to its original bytes. This reports historical success and current drift separately; it does not establish that the subsequent change was approved or harmless. Inspect changed_files and current_snapshot_matches before any follow-up work. A target with no verified receipt and unexpected bytes remains conflict and needs review. Do not infer a verified historical save merely from matching candidate bytes without a receipt.

Pending statuses applied, rejected and superseded remain closed during history replay. Linked proposal details still show current drift, but do not reopen the item. A linked verified receipt establishes applied for an otherwise open item even when a later edit has changed the target. Changes needing follow-up use a new candidate referencing the prior item in its private facts or sources; never rewrite old receipts or reopen completed work to track the new change. Status and list only read evidence and must not rewrite records, pending events or receipts.

If legacy history contains an event attempting to change a terminal status, replay preserves the closed status and reports the event filename in ignored_reopen_events. The original event remains untouched for audit; no migration rewrites private history.

Recovery verification requires the target to remain in the current approved_files subset, an actual prior approved apply attempt, its confirmed target-write marker and the verified original backup. It does not gain permission from an old receipt or rewrite records. If scope was removed, stop and explain the current restriction; do not silently re-enable the file. An already verified receipt is not replaced: verify checks current scope and snapshot, reports validation_run false, and preserves the historic receipt. If the snapshot has changed, use status to explain the drift instead of certifying current consistency.

Regression tests are across tests/test_*.py, including proposal, baseline-error and stable-error cases. They use synthetic records and simulated fixture-only approvals. Run with an authorized existing Python; set TEST_RSCRIPT and optional TEST_R_LIBRARY for real R/yaml integration, and TEST_TMP_ROOT to a short authorized private scratch directory when OS temp is restricted. No production approval or record access is implied by running tests.

## Failure before the target write

`failed_before_write` records a failed apply without confirmed target-write evidence, or an unconfirmed attempted apply whose target still matches the original baseline. A recorded failure remains failed even if a later proposal independently saves identical candidate bytes. Hashes alone do not prove that no transient write occurred. A confirmed write later externally restored to baseline is conflict, not a pre-write failure. The proposal cannot be reapplied, even when its backup matches. Inspect status, backup and the actual failure cause; preserve the old proposal, approval evidence, attempts and backup. After resolving the cause, run `propose` again against current sources, show the new proposal ID/diff/validation and obtain new exact approval, even when the diff is identical. Do not reuse the previous approval, delete attempts/backups to reset status, or automatically roll back.

A fresh proposal is not recovery for `saved_unverified`: the requested bytes are already present. Inspect that status and use the reviewed `verify` path without rewriting when its current-scope, evidence and validation checks permit it. Conflicts or uncertain outcomes require reviewed reconciliation.


## Correcting records with pre-existing validation errors

Baseline validation records errors instead of blocking every correction. A candidate may remove baseline record errors and may retain only errors tied to the same diagnostic and unchanged affected record content. The proposal displays error_review.remaining_errors and resolved_errors alongside readable baseline/candidate validation. Show these before exact approval; never hide inherited errors or silently repair unrelated records. A verified save means the approved change passed this comparison, not that the whole dataset is error-free.

The R validator still exits nonzero on any error for standalone callers. It also emits a complete versioned diagnostic report; the helper checks that report, exit status and human-readable error messages agree. YAML parsing, inaccessible/missing input, invalid top-level sequences and malformed record mappings remain blocking structural failures. Missing, malformed or incomplete reports, unavailable R/yaml and process failures are not tolerable baseline errors.

Error identity binds severity, the diagnostic message with only its leading supported-table row label normalized, and the full serialized affected record. Row numbers remain unchanged in human-readable messages. Newest-first insertion or reordering may retain an unchanged record error; file name, field/value diagnostic details and record contents still distinguish errors. Error occurrences are counted, so an added identical bad record or repeated diagnostic cannot hide behind an existing occurrence. Resolved/remaining lists preserve occurrence counts. Changing a record that still has an error requires resolving that record's errors; this conservative rule can reject an unrelated field change in the same invalid record. File-level duplicate-ID errors remain bound to the entire file's parsed content and are not relaxed by row-label normalization. No baseline parser failure can be used as an approval exception. The existing V1 diagnostic protocol is retained; no stored proposals or receipts are rewritten. Older diagnostic reports can be read under this comparison, while exact source snapshots, candidate hashes, approval evidence and later-gate occurrence equality remain required.

Before apply, compare staged validation with the reviewed candidate errors, then validate the candidate against a stable current bibliography. After save and during verify recovery, require the same reviewed error identities and warnings; any addition, removal or changed identity at these later gates requires renewed review/reconciliation. Never adapt an approved error baseline automatically. Source hashes, target bytes, scope, approval evidence and backups remain independently enforced. A saved_unverified target is retained if later validation fails; recovery does not rewrite it. Older successful proposals with no structured diagnostics tolerate zero errors, and old receipts remain unchanged. Standalone validator output and raw diagnostic context stay in private operation evidence; readable proposals omit machine context lines.

## Recovery write attribution

New apply attempts use write_evidence_version=1 and target_write_confirmed=false before backup/write. Only after atomic replacement returns and the candidate target hash matches does the helper persist target_write_confirmed=true and target_written_sha256 for that same proposal, before final validation. Receipt-only recovery requires these markers and all existing approval/backup/current-scope/snapshot/validation checks. They are local operation evidence, not independent authentication or protection against a writer who can forge private state. No hash match from another proposal can substitute for them.

An interruption after replacement but before durable write confirmation is an uncertain outcome. Even if current candidate bytes match, verify refuses a recovery receipt when evidence is missing. Preserve the file, attempts and backup for manual reconciliation; never fabricate a marker, copy another proposal’s evidence, blindly retry apply or overwrite the target. Legacy interrupted attempts without this evidence also require reviewed manual reconciliation; no automatic history migration/backfill is supplied. A saved_unverified status reports matching bytes, not necessarily attributable authorship of the save.

Previously completed receipts stay immutable. If an older recovered receipt contradicts an explicit failed_before_write attempt without confirmed write evidence, status reports conflict, write_attribution=contradictory_recovery_history and historical_save_verified=false. It does not delete/repair the receipt or rewrite pending history. Investigate both proposal histories and create a separate reviewed reconciliation record; do not certify the failed attempt from later identical bytes. Other genuine prior receipts continue to report historical success and later drift independently.

Regression coverage includes tests/test_recovery_attribution.py and tests/test_failed_recovery.py, including real R/yaml validation. It checks a failed A followed by identical successful B, unconfirmed legacy recovery, contradictory existing recovery receipts, pending-item attribution and confirmed writes followed by external restoration. Legitimate confirmed post-write recovery remains covered by tests/test_proposals.py.

## Explicit bibliography scope
The proposal helper passes an explicit bibliography path when configured, or --no-bibliography when the profile setting is null/absent. Null consistently keeps manuscript-reference checks incomplete with a visible warning, even if publications.bib exists or appears later. This preserves the reviewed source scope and avoids silently reading an unconfigured export only after saving. Configure the intended bibliography through a separately reviewed preference change to enable key checks. Standalone validate.R with only DATA_DIRECTORY retains its publications.bib default; its optional --no-bibliography argument explicitly disables that fallback. No profile, export or historical proposal/receipt is migrated by this fix. Older already-saved proposals retain their original reviewed diagnostics; any mismatch still needs reconciliation, not automatic rewriting.

## Legacy recovered receipts without attributable write evidence
An existing recovered receipt is not historical proof when none of its own attempts has matching versioned target-write confirmation. status reports legacy_recovery_unattributed and historical_save_verified=false, regardless of matching current bytes, an applying or saved_unverified legacy attempt, missing attempts or later drift. No attempt/receipt/record is rewritten. An explicit failed_before_write contradiction still reports conflict/contradictory_recovery_history. Ordinary non-recovered historical receipts and recovered receipts with their own confirmed target write retain their existing semantics.

verify refuses to certify or replace an unattributed legacy recovered receipt. Inspect evidence and use separately reviewed manual reconciliation; do not fabricate markers, migrate history or reapply the old proposal. Nonterminal linked pending items show needs_review (deferrals stay deferred). Explicit historical terminal pending events remain immutable; the read-only view adds historical_reconciliation_required=true and historical_save_verified=false rather than silently reopening or certifying them. list/status/verify never rewrite those histories. This plugin fix does not authorize inspection or repair of a real private proposal history.

## Exceptions before target writing begins
Apply tracks whether this attempt entered atomic_write for its target. Backup, final source/evidence checks and candidate-byte reading happen first. An exception before entering the write records failed_before_write regardless of current hashes, including an identical save by another proposal in that interval. It retains backup/attempt/error evidence, cannot be reapplied or verified as a saved write, and leaves a linked nonterminal pending item needing review. No record rollback or history migration occurs. Once writing is entered, existing hash/attribution checks still govern: ambiguous or post-write failures must not be labelled definitively pre-write. A hard kill before an exception handler runs remains subject to the existing durable-evidence/manual-reconciliation policy; the local flag is not new crash-proof evidence.


## Manual reconciliation of an unconfirmed write
Use this only for a reported interruption and specifically authorized proposal/state access. It does not authorize a broad private-history audit. An interruption after replacement but before the durable write marker cannot be resolved by matching bytes alone. This is an intentional evidence boundary, not an automatic recovery opportunity.

1. Pause dependent writes. Inspect status and preserve the current record, proposal, approval evidence, attempts and original backup. Do not reapply the old proposal, restore a backup automatically, fabricate a marker or edit an old receipt.
2. Compare the actual current record with the staged candidate and original backup; check current permissions and relevant consumers. Validate the current source read-only with the configured R validator and explicit bibliography scope (configured path, or --no-bibliography). Report actual current errors/warnings and any conflicting edits. Current validation does not prove who performed a past write.
3. Show the current-state comparison and ask one focused question about accepting those exact current facts or preparing a correction. Existing approval of a prior candidate is not proof of historical execution. If unresolved, keep the item pending and preserve the files.
4. If the user accepts the current state, leave the source bytes unchanged. Save a separate dated private reconciliation note outside the old proposal folder, containing the actual response/reference, proposal ID, current file/hash, validation evidence and unresolved attribution. Label it current-state acceptance, not a historical save receipt. The original status may remain saved_unverified/unconfirmed; do not set historical_save_verified or rewrite history to make it appear completed.
5. If a correction is needed, prepare a fresh proposal from the current live sources and obtain new exact approval. If no byte change is needed, do not manufacture a no-op proposal or save merely to obtain a receipt. A linked pending item may be explicitly superseded with the user's actual disposition and reconciliation-note reference; do not mark applied without the required attributable save evidence. Preserve any existing terminal events.

This is an agent-guided manual procedure, not a reconciliation helper, authenticated attestation or automatic history migration. It makes future work possible from an explicitly reviewed current baseline while keeping historical uncertainty honest. Other conflicts, changed permissions or failed validation remain blockers to dependent changes. No live reconciliation runs merely because the plugin was updated.
