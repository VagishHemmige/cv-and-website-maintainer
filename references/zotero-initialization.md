# First-time Zotero publication setup

Use when publications are in scope and Zotero is chosen or being considered. First reuse existing profile/bootstrap answers; ask only the next unresolved question through supported question UI. This is coordinated agent work around existing skills, not a second Zotero connector or an automatic CV parser.

## Check separate capabilities
Read the current installed Zotero skill and use its status/probe read-only. Distinguish Desktop missing, installed/stopped, running but API unavailable, missing/limited integration, and a complete empty/existing/unknown library inventory. Do not equate a ChatGPT plugin being installed with an accessible library or writes. A limited/failed library read does not establish an empty library. Check library identity and full pagination before deduplication.

No online Zotero account is required for local Desktop library use. Ask about account/sync only if the user wants online access, sync or a route that needs it. Do not request API keys/passwords for the local no-account route. Installing Desktop, connecting a plugin, enabling local API/restarting Desktop and creating collections are concrete host actions: explain and obtain actual scope authorization, reusing an already matching setup approval. The academic update workflow's stricter connection/approval rules govern over a companion's convenience defaults. Use current official [installation](https://www.zotero.org/support/installation), [basics](https://www.zotero.org/support/quick_start_guide) and [sync](https://www.zotero.org/support/sync) guidance. Never silently install, enable sync or move the Zotero database into the site.

If missing, offer authorized setup or continue private source reconciliation and retain the connection as pending. Optional Zotero setup must not block unrelated ready capabilities. If publications/authority are undecided, ask rather than assume Zotero; preserve another established authority pending an explicitly reviewed migration.

## Build or reconcile the publication list
Confirm the historical CV/publication source and exclusions under initialization's privacy/private-processing rules. Extract publication segments into the existing coverage ledger with target=zotero. An initial empty library is populated only through reviewed real candidates, never dummy items. Existing libraries are reconciled, never reset.

For each CV citation, resolve DOI/PMID and authoritative PubMed/publisher metadata; preserve authors/order, type and source date precision. Search titles/identifiers even when author search misses a chapter or unindexed article. Explain missing essential metadata and keep ambiguous matches pending. Books/chapters and non-PubMed outputs need publisher/ISBN or clear user evidence; do not force them into journalArticle. Distinguish preprint, ahead-of-print, final article and corrections.

Offer PubMed author discovery to identify CV omissions using confirmed name variants, affiliations/identifiers and topic context. Obtain actual source/search-window scope; use discover-academic-updates and its checkpoint rules for broad searches. Targeted citation lookup is distinct from a claim of exhaustive career discovery. Check indexing/update dates where supported and disclose coverage gaps. Do not claim every publication was identified.

Reconcile the merged CV/search set within itself and against the whole relevant library using the existing update-zotero-records DOI/PMID/title/version checks. Track each source citation as matched existing / proposed new / correction / uncertain / excluded with reason and evidence. Keep correspondence/extraction private. Reuse private candidates and confirmed decisions on resume; no repeated duplicate proposals. No metadata-only PDF downloads.

Show the exact proposed new items and destination, uncertain matches, excluded sources and expected CV/site coverage. Import only through update-zotero-records after exact approval and immediate duplicate/destination/export-side-effect rechecks. The library root/no-collection choice is a real destination, not permission to use whichever collection happens to be selected. Reuse an existing item without importing another copy. Current read-only routes do not edit existing metadata; do not reimport corrections as duplicates.

After any uncertain timeout or partial batch, read back identifiers/items and reconcile outcomes before retry. Capture approved payload/import session/item-key evidence privately; never create dummy real-library items for a test. Account creation, connector availability or successful import response alone does not establish verified library population.

## Export and citation keys
Ask which publication subset should feed the CV/site: a selected collection, reviewed item set or whole library only if it is truly the intended subset. Inspect existing export targets/automatic side effects before library writes; resolve unknown effects under the Zotero protocol. A personal general research library often contains many papers not authored by the user.

Inspect actual export capabilities. Current companion export-bibtex has --item-key and whole local-library output, not a collection filter or arbitrary group-library selector. Do not invent flags or assume UI-selected collection controls export. For a collection/group/reviewed subset, use a supported scope-aware route or guide native Zotero collection/selection export, verifying selected item membership. Keep unsupported export capability pending. Native UI/manual export is a valid fallback; do not require a new account or Better BibTeX.

Default to a reviewed manual export unless the user chooses automatic export. Better BibTeX is optional: explain stable-key and auto-export benefits, check current [Better BibTeX guidance](https://retorque.re/zotero-better-bibtex/exporting/auto/), and obtain installation/configuration authorization. Do not add that dependency or enable automatic writes silently. Existing auto-export behavior must be verified rather than disabled, replaced or assumed absent.

Export first to a unique authorized private staging file. It is a generated derivative of Zotero, never a competing publication authority. Check BibTeX parsing using the actual R consumer, unique/nonblank citation keys, expected item count/identifiers, complete authors/type/date, excluded records, and no file/attachment/private-path/contact fields. Zotero item keys and BibTeX citation keys differ; keep a private mapping where established, preserve used keys and check mentoring/manuscript references before any key change. Do not hand-edit generated metadata or fabricate missing keys as a substitute for fixing export configuration.

Inspect the starter's actual data/publications.bib, site.yml and R/page bibliography consumers; existing projects can use other paths. Propose exact export destination and consumer/profile changes, backups and overwrite/refresh behavior. Copying an export into data/ is a separately approved generated-export action, outside routine YAML helper scope. Never overwrite an existing export or create a second competing .bib implicitly. Use authorized host tools and current project instructions; stage precise edits when parent/source writes are owner-managed.

Run authorized R CV/Quarto commands and verify expected publications, author emphasis/order, grouping and links in both requested outputs. A parse or successful render is not proof all selected works appear. Account for legitimate exclusions/filters via the initial output-coverage table. Verify export freshness and establish how the next approved Zotero change reaches the outputs. Public-CV handling remains separate.

## Reuse or guide export configuration
At initialization, first ask whether an export already exists only if saved answers and accessible observations do not settle it. Existing setup takes precedence over the new-user manual-export default. Inspect/reuse it; do not create another export, reset settings or repeat the questionnaire. A user's confirmation establishes configured intent, not live verification.

Record the actual source library/collection (and subcollection behavior where relevant), translator/format, exact absolute destination(s), citation-key policy, enabled state, execution timing (on change/on idle/paused), latest status/error and evidence date. Compare the source membership with the approved import destination and intended publication subset. An item imported at the library root does not automatically join an exported collection. Record all observed automatic side effects, including any Better BibTeX Git integration; do not enable automatic commit/push under export-only permission.

If no export exists, offer Better BibTeX automatic export or native/manual export. When automatic export is chosen, consult current official installation/export guidance, explain and obtain matching installation/configuration and destination-write authorization. Guide the user one step at a time: install Better BibTeX if needed; select the intended library/collection; choose its Export command; choose the compatible Better BibTeX translator; select Keep updated; and select the exact reviewed bibliography destination. Review the resulting entry in Better BibTeX preferences, Automatic exports, including timing. Setting up an export can immediately overwrite a file: review the destination, existing bytes and backup before this step. Do not promise a companion tool can configure settings it cannot access; use authorized UI assistance or precise user instructions. The automatic-export management tab manages existing exports; initiating an export creates one.

For an already approved existing automatic export, read/validate its actual destination in place or a private snapshot; do not demand replacing it with a staged export. Private staging applies to new/manual export proposals, not silent reconfiguration of existing automation. No dummy publication is needed: use existing real records for initial verification and the next genuine approved addition for incremental verification. Native/manual export remains valid without Better BibTeX.

Persist the verified setup, user choices, evidence date and any pending checks in the existing private profile authority and linked setup note through reviewed profile safeguards. Do not introduce a second profile or mandatory new config schema. On routine weekly runs reuse those choices: check relevant accessible status and coverage, report meaningful failures or changes, and ask setup questions only when a changed setting, failure or unresolved dependency requires an answer. Scheduled discovery remains report-only.
