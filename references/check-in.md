# Review message and guided update conversation

Use this workflow for an interactive maintenance check-in and for the tasks configured by setup. Load the user's notification/reminder preference. The questionnaire must offer a regular submission reminder even when searches find nothing; do not assume quiet-no-change behavior for every user.

## Message sequence
1. Present evidence-backed suggested updates from authorized discovery/searches and relevant checks first. State sources actually searched and important coverage gaps. Distinguish candidates, unresolved facts and proposals; no automatic writes.
2. Include a link to the latest verified existing CV output and a link to the user's actual website. Read output paths/URLs from the profile and inspect existing outputs as access permits. Clearly label known stale outputs or freshness not verified. Never call an output updated merely because records changed or choose a style reference/historical baseline as the current CV. A public CV link requires a reviewed public version; private local CV links are only for an authorized private host/session. Never upload/publish a CV to make a link work.
3. Present the checklist of applicable record categories, each category label linked to its actual authoritative YAML for inspection in the host side panel when supported. Include grants, teaching, presentations/talks, abstracts, mentoring, projects, appointments, service, education, training, certifications, memberships, honors and optional media as applicable. Do not invent YAML destinations: publications use their configured authority, such as Zotero, with a separate appropriate viewing/update action.
4. Invite the user to submit any activities/corrections the searches missed to the assistant. This is not a request to manually edit their CV, website or YAML. Category selection guides the conversation: open the requested source for inspection, show relevant current records when needed, distinguish add new from update existing, then ask only the next missing fact. Reuse update-academic-records or update-zotero-records for the reviewed proposal and approval workflow.
5. Offer Nothing to add this week (or None of the above). An explicit response closes that check-in's manual-submission portion only; it does not approve/reject unrelated proposals, resolve outstanding source findings or confirm all existing facts. An ignored reminder receives no extra nudge in that same weekly cycle. Next scheduled cycle may issue its normal reminder. Maintain a stable cycle ID to avoid duplicate same-cycle dispatches.
6. On the broader every-N-cycle review, add the due status/completeness sweep and deeper cross-checks under reviews.md. Routine lightweight validity/reference checks may still run weekly. The broader cadence never restricts viewing YAML, CV or website or submitting an update on any day.

## Host behavior and honest fallback
A checked Markdown box is not inherently an interactive control. Use a real supported checklist/selection UI if available; otherwise render linked category labels and let the user reply with a category name. Do not claim a file-open event automatically reports a selection to the assistant if the host has no callback. In that host, let the user click to inspect the file and reply with the category/update; supported follow-up actions can combine opening a file and starting the update conversation when actually available.
On Codex, open_in_codex with a file target can open a selected existing YAML in a side panel when invoked. Ordinary absolute workspace links may provide viewing; validate actual file existence. If click-to-panel control is unavailable, offer the host's supported viewer or a read-only excerpt and state the limitation. No fabricated links, simulated buttons or claimed custom app UI.
YAML viewing is available on demand between check-ins. Viewing/selecting is not edit authorization. Preserve exact-proposal approval and actual host permissions. Keep raw source correspondence/PHI out of messages and public records.

## State
Resolve CV links and index new output evidence using [CV selection and output observations](cv-output.md). Read check-in-status.output_observations before presenting links, then recheck the actual file/site. Date-stamped discovery requires a separately approved cv_locator; a fixed cv_link never silently becomes a directory search. File modification time or a matching report hash does not certify current CV contents. Keep known stale/missing/ambiguous outputs explicit.

Store reminder/notification mode, links and freshness evidence, category-to-source mapping, cycle ID, dispatch time, selected categories, manual-submission completion/ignore state, outstanding candidates and broader-review due state privately. Record confirmed user preferences, not packaged personal defaults. Unknown output freshness remains unknown. Do not record a CV/site as regenerated without actual evidence.

## Supported progress storage
Stage actual routine no-change answers and batch their history writes through [confirmation batching](confirmation-batching.md). Consult check-in-status.no_change_confirmations and retained staging on resume. This is separate from dispatch/closeout, broader completion, deferrals and exact-proposal approvals.

Use packaged commands and small private JSON inputs instead of generating custom Python wrappers for routine confirmations or saves; follow [routine save and consumer-inspection reuse](routine-save.md). Do not create a competing check-in-confirm store or skip current source/approval checks.

Use [private-state runtime commands](private-state.md#routine-check-in-progress). Read check-in-status before dispatch; record actual operational events with check-in-record in STATE/reviews/check-in-state.json. Never save cycle IDs, manual closeout or broader completion into config.json. Cadence, reminder mode, viewing links and category/source mapping remain reviewed preferences. Keep freshness/check evidence in private reports referenced by events. Nothing to add closes only that cycle's manual submissions; ignored cycles retain findings. Mark broader completion only after the actual sweep. Consult pending broader-due cycles and carry unanswered work forward. Existing nonnull legacy progress requires reviewed migration, never silent copying/deletion.


Deferred questions follow [structured deferrals](deferrals.md): reuse saved decisions and ask only when the agreed date or named condition permits. A new check-in does not reopen a dismissed candidate or override a pending deferral.
