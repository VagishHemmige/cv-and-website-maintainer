# Teaching, abstract and presentation attachments

New public PDF saves require a private [approval evidence file](approval-evidence.md) linked to the exact attachment ID, PDF hash and destination, with explicit public-use approval. The helper stores the quoted response/context before copying, references its hash in save-attempt.json/saved.json and checks it in status. This adds audit evidence, not authentication or automatic privacy clearance. Existing receipts are preserved; missing evidence is reported without inventing approval. Interrupted copies still need reviewed recovery, never blind retries or overwrites.

For every new teaching activity, abstract or talk, ask once: “Would you like to attach a PDF or PowerPoint now, add it later, or have no attachment?” An already supplied attachment answers the question. Do not delay an otherwise complete record for an optional file. Keep its existing pdf/slides field null and record the choice privately; do not add attachment-status fields to public YAML. Use the structured question capability for the now/later/none choice when available. If the user chooses now, request the actual upload in normal chat; text-only question tools cannot receive files. Do not ask the attachment choice again when a file was already supplied.

## Access and destinations

Read project instructions, current YAML and consumers. Check actual read/write access to the data and resource folders. Installation and a configured path grant no access. For a write probe use an exclusively created uniquely named temporary file; remove only that probe. A prior check is not proof of future access. Local authorized tools are required; when unavailable, keep the file/link request pending and explain what access is missing.

Attachment destinations are a separate, explicitly authorized scope from approved_files. Save project-relative, case-sensitive PDF directories under attachments.approved_pdf_dirs in the private profile, plus attachments.routes keyed by teaching, abstracts and talk categories. Paths in public YAML resolve from the project root, never from data. Do not package personal paths in this plugin.

Conventions to verify for each project:

| Record | Field | Typical PDF directory |
| --- | --- | --- |
| teaching.yml | slides | teaching |
| abstracts.yml | pdf | abstracts |
| talks.yml, invited | slides | presentations/Invited talks |
| talks.yml, conference | slides | presentations/Conferences |
| talks.yml, teaching | slides | presentations/Teaching |
| talks.yml, grand_rounds | slides | Ask or reuse a confirmed route; no universal directory |

Inspect existing subfolders and linked paths before choosing. Category teaching in talks.yml does not move an activity to teaching.yml. Do not infer the category from the upload filename. Empty or missing routes need clarification. Do not create new directories, reorganize existing resources or overwrite a file implicitly. Original PPT/PPTX files may remain in private staging only after explicit approval of the private-copy/conversion step described below; this approval is separate from public placement. Archiving originals into an existing ignored raw folder requires separate user authorization and verified ignore rules; a folder named raw alone is not privacy protection. Do not link to raw files.

## Prepare and review

Match the file to exactly one existing record or the proposed new activity, using stable ID where present, otherwise title plus meeting/venue and date(s). Ask when ambiguous. Never infer authors or event dates from filenames. Inspect the material for suitability for public website linking, including patient identifiers, speaker notes and unpublished content; do not silently redact or publish it. Ask whether the reviewed PDF is intended for the public site as part of the exact proposal.

Read [mandatory privacy warnings](privacy.md) before upload and preparation. Initial source screening checks what is available in the source (including filename, text, notes/comments and visible content where accessible); it is not a claim of complete visual review. If already flagged, warn and stop before copying or conversion. For PowerPoint that is not flagged by this initial screening, explain that the helper must create an ordinary private copy and converted PDF before final visual review, and obtain explicit approval for that preparation. If the user declines or this storage is unsuitable, request a de-identified PDF exported locally with institution-approved tools instead.

For an initially not-flagged PowerPoint with actual private-copy approval, run `scripts/attachments.py stage STATE SOURCE RELATIVE_PDF --source-screening not_flagged --private-copy-approved`. The helper rejects PowerPoint lacking either assertion before creating its attachment folder or probing converters. `--source-screening flagged` rejects any supplied format before copying. These are operator assertions of real screening/permission, not automated PHI detection or authentication. The PDF-only route also requires an actual initial not-flagged source review and must use `--source-screening not_flagged`; full public-use review is still required. Never turn a flagged or unscreened PDF/deck into not_flagged merely to bypass the guard. All new PDF/PPT/PPTX staging rejects missing/not_screened assertions before folder creation, private copying, PDF parsing or converter discovery. This is a workflow assertion of the actual initial review, not automated HIPAA detection or complete visual clearance. Existing staged copies/receipts are preserved; no automatic migration, deletion or retroactive clearance is performed. Final privacy review and exact public-use approval remain separate.

Preparation creates a private `staging.json` receipt and original/converted files; a successful manifest explicitly remains `pending_visual_privacy_review`. Conversion success is not privacy clearance. Before saving/linking, inspect every converted page visually plus extractable text/metadata and accessible original notes, hidden slides/comments and embedded objects; hold public placement when review surfaces remain unresolved. If possible identifiers are found after copying, explicitly warn, give the private folder location without reproducing identifiers and pause saving/linking. Do not make further flagged copies or automatically delete the folder; request permission for cleanup and a de-identified replacement. Conversion or validation failures likewise identify retained private staging and write a minimal `staging-failed.json` with failure phase/category, without dumping source content or converter output. A failed preparation may have no manifest: inspect the preparation receipts directly rather than blindly retrying stage or assuming nothing was saved.

The helper accepts PDFs and .ppt/.pptx. After PowerPoint input-format validation, first probe the PowerPoint COM registration on Windows, including Microsoft Store installations; checking PATH or conventional Office folders is insufficient. The helper uses a local PowerShell runtime and convert_powerpoint.ps1 to open a read-only untitled copy with macros disabled and export a PDF. It prefers pwsh when available, respects execution policies and does not close preexisting PowerPoint sessions. If PowerPoint is not registered, use an already installed LibreOffice converter (auto-detected or privately configured as attachments.soffice), with a separate temporary user profile. Host approval may be needed for desktop automation; do not misreport a permissions failure as an absent installation. Do not install software or upload slides to external conversion services without authorization. If neither converter is usable, explain the actual failure and ask for a PDF or leave the attachment pending. Do not assert that no converter is installed after only a PATH/common-folder check. A failed export is not silently retried through another engine; inspect and resolve the failure first. Renaming an extension is never conversion. Preserve the original, inspect the converted PDF page count and render/visually check its pages using available PDF tools, especially fonts, cropped text, figures and poster dimensions. Report incomplete visual verification. The helper requires pypdf and does not itself render pages.

Show the exact YAML diff through the existing proposals.py workflow, staged PDF name, destination, source filename, PDF hash/page count, conversion method and public-use question. Get explicit approval for both PDF placement and the YAML diff; a general request to add an activity is not approval of unseen content. The existing YAML approval policy remains per_change. Recheck source hashes immediately before applying. Run attachments.py save STATE ID --approval ID --approval-evidence FILE --privacy-reviewed --public-approved only after completed privacy review and actual explicit public-use approval. These flags are operator assertions, never authentication or automated PHI detection. It rejects altered staged bytes, changed attachment authority and existing destinations. Reuse an existing identical PDF only after verifying its bytes and intended record association; use a fresh filename for a different version. Never delete the previous version automatically.

New manifests record save_scope_version=1 and save_scope_sha256 for the resolved project_root, validated per_change approval policy and the complete attachments object. Object-key ordering and JSON formatting do not affect that hash. Changes to check-in cycles, setup answers, discovery selections or unrelated runtime settings do not invalidate the reviewed PDF; saving reuses the same staged bytes and does not reconvert or make a new private staging copy. All attachment settings remain conservatively relevant, including approved directories, routes, converter configuration and future attachment-specific keys. A settings/authority change requires reviewed reconciliation and renewed approval, not silent rebinding. The helper rechecks the current project, policy, route, scope hash and staged bytes after PDF parsing and before exclusive public-file creation. These checks do not lock unrelated editors or eliminate every filesystem race.

The original whole-profile config_sha256 remains private staging evidence. Legacy manifests without the versioned scope fields still require that original full-profile hash to match; if it differs, the helper cannot establish the prior relevant settings and refuses rather than silently migrating approval or rewriting the manifest. Explain that limitation, inspect the existing private staging and agree a reviewed reconciliation path before making additional copies. Unknown/incomplete scope versions also fail closed. Status reports byte/destination state; it is not an approval or guarantee that current save-scope checks will pass. No plugin update automatically changes existing manifests or public PDFs.

Save and hash-verify the PDF first, then apply the approved YAML proposal. Do not put a live link to a missing file. These are two operations, not an atomic transaction. If YAML apply fails, retain and report the saved but unlinked PDF, reconcile the YAML proposal status, then prepare a fresh exact proposal if needed. Do not delete the PDF or retry blindly. If the PDF copy is interrupted, use attachments.py status STATE ID to compare staged and destination hashes before any retry. Partial destinations require a reviewed recovery plan; never overwrite automatically. For a resource link-only YAML change, the existing validator still checks data; separately verify the linked file at project_root / relative_path because staged data is not a staged website.

The attachment helper permits only new PDF files in exact approved directories inside abstracts, teaching or presentations. It does not edit YAML, change folder permissions, archive originals, render the site, generate a CV, commit or publish. Files saved in the public repository may become public in the owner's next publication.

## Add later and recover across chats

When the user selects later, use proposals.py remember with kind attachment, facts containing the record file, exact selector, intended pdf/slides field, confirmed route (if known), choice later and any linked record proposal ID. Use missing_fields [attachment] and one focused upload question. Keep pending state outside the public repository. A record proposal completing does not complete its separate attachment item. When the user chooses none, record that decision and do not repeatedly ask on routine edits.

Trigger this same workflow for “add the slides later”, “attach this poster to my existing abstract”, “replace the PDF” or an upload referring to an existing activity. Reopen pending state and search live YAML again; reconcile title/date edits since deferral. If pending state is unavailable, match from current records without creating a duplicate. Approval covers only the attachment and minimal pdf/slides link edit unless other changes are explicitly proposed. Preserve teaching dates lists, authors, mentees, categories, titles and anchors. For an existing non-null path, show old and new paths and preserve the old file. Close the pending attachment only after both file and link are verified. Use an applied event referencing the verified YAML link proposal and an event note identifying the attachment receipt/hash. The earlier record-creation proposal alone cannot complete a deferred attachment. If the link already existed and no YAML proposal was needed, record a superseded event with a note explaining verified existing association and receipt; never invent a proposal or a save.

Report the saved file, changed record, checks and any remaining pending step. Website/CV generation, Git and publication follow the user's saved assistance preferences and separate stage authorization under [output follow-through](output-execution.md). Attachment approval alone does not authorize these stages. No scheduling is implied.

When repeated teaching sessions use different decks, ask which session/version the file belongs to. The current single slides field does not encode per-session materials. Preserve the record and hold unsupported associations for a reviewed schema/consumer plan; do not overwrite the latest link as a guessed policy. A single underlying work at multiple meetings similarly requires confirmed occurrences and compatible representation.


## Interrupted attempt with no destination
After an interrupted save, inspect status first. An intact save-attempt.json plus unchanged staged PDF/evidence and no public destination reports save_interrupted_before_copy, not awaiting_approval; resume_available additionally checks current scope. This label describes the currently absent destination, not proof that no historical copy ever occurred. Invalid/truncated attempt or approval evidence reports save_attempt_invalid and cannot resume. No receipt/history is rewritten by status.

For an inspected resumable attempt, use save STATE ID --resume with the same --approval ID, original exact --approval-evidence FILE, --privacy-reviewed and --public-approved assertions. Existing actual approval of those unchanged bytes/destination must still apply; the resume flag is an operator assertion, not new approval or privacy clearance. The helper reparses the existing private PDF, rechecks current route/scope/hashes and original evidence/attempt, preserves the original attempt, and exclusively creates the absent public PDF. It uses the shared private-state writer lock; never clear an unknown writer lock to force resumption. No restaging/private-copy duplication is needed.

A partial/conflicting destination requires reviewed reconciliation without overwrite/deletion. Matching public bytes with no saved receipt remain a separate post-copy review case: --resume does not copy again or mint a receipt from matching bytes alone. A completed saved receipt followed by a missing file remains missing_after_save and is not implicitly republished. Scope, staged bytes, evidence or destination changes block resume. YAML linking still needs its own approved record proposal.


## PowerPoint input-format guard
After actual initial screening/private-copy approval, but before private folder creation, copying or converter discovery, staging checks the source format and binds the checked bytes to the subsequent copy by SHA-256. PPTX needs a bounded readable ZIP, unique safe part names, recognizable content types, an internal officeDocument relationship and a PresentationML presentation root. All archive entries are read without extraction to check CRC/truncation. Encrypted/oversized packages and DTD/entity XML are refused. Transitional and strict presentation namespaces are recognized. This is basic format recognition, not full Office schema validation, malware detection, de-identification or visual clearance; a structurally recognizable deck can still fail conversion.

Legacy PPT additionally requires the optional local Python package `olefile` to inspect compound storage, PowerPoint streams, CurrentUser header and its UserEdit reference. If unavailable, block before copying/conversion and request a locally exported PDF/PPTX or ask for authorization to install it; do not silently install or bypass validation. A renamed Word/Excel/ZIP file or corrupt deck cannot be accepted solely because a converter creates a PDF. Format rejection does not delete or modify the original. Existing staged files are not migrated or retrospectively certified.
