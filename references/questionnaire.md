# Conditional questionnaire and initializer coverage

First-time users can now use [initialize-academic-records](../skills/initialize-academic-records/SKILL.md) for a resumable pre-project interview, private CV text extraction/coverage ledger and prototype starter staging. See [initialization](initialization.md) for commands and limits. These staging commands do not create a real project or deploy it. The [reviewed execution branch](setup-execution.md) supports approved new-project creation, local commands, Git commits and gated push; account/repository creation and deployment configuration/verification use authorized host tools. Automatic factual CV import is not supplied. Existing maintenance must not restart initialization.

This is an inventory of decisions, not a form to show at once. Follow questions.md: one active question, save its answer privately as pending under preferences.md, then resume the next necessary item. Combine confirmed answers into one exact profile proposal at a checkpoint; pending interview answers do not update config.json. Reuse confirmations and inspect facts available through authorized tools. Unsupported initializer capabilities remain planning, not promised actions.

## Entry and capability readiness
Determine whether the request is maintenance, preference setup, initial CV/site reconciliation, or a fresh project. Existing-project maintenance must not restart import. Maintain readiness per capability: local record updates, discovery, publication integration, attachment placement and scheduling. Overall setup may remain incomplete while a ready capability works.
For each capability, record ready/pending/unavailable with evidence and blockers. Do not call a capability ready solely because fields exist: inspect consumers, runtime and access as appropriate. Setup cannot grant permissions.

## Conditional user choices
| Branch | Resolve when needed | Preserve |
| --- | --- | --- |
| Starting point | Existing project versus reconciliation versus fresh start | Existing infrastructure, unrelated work and unsupported initializer status |
| Import baseline | Confirm a historical CV and supporting sources only when importing | Account for each baseline entry: represented, missing, conflicting, excluded or unresolved; never import generated CVs back |
| Output goals | CV only, website only or both; relevant formats/templates | Existing approved layout; output setup remains separate authorization |
| Visibility | Public versus private/CV-only material and excluded content | Private contacts and unpublished material outside public repo; hidden fields do not protect committed bytes |
| Assistance | Instructions, prepared reviewable changes or authorized execution for each action class | Separate record, code, render, Git and publication choices; preferences never bypass current workflow scope or exact approval |
| Publication gate | Recommend human preview for new users; offer explicitly authorized agent-verified publication | Explain that the latter can push without another confirmation before the user sees the preview; reuse existing choices and leave an undecided choice pending, following setup-execution.md |
| Storage/host | Private profile/history location, current project/computer and handoff; optional backup/transfer | Inspect existing profiles and jobs first; choose an authority before merging |
| Search identity | Confirm name variants, identifiers and affiliations that resolve real ambiguity | Optional null clues alone do not block a usable search or reopen setup; ask only what resolves actual uncertainty, preserve deferrals and exact profile approval; no surname-only identity assumptions |
| Sources | Source types and exact email/calendar accounts, chats/projects, rosters/repositories and exclusions | Discover integrations each run; scoped one-off permission is not permanent recurring access |
| Review categories | Projects, mentees, roles/service, grants, credentials, pending activities and public descriptions | Users may have no project or mentee list; do not block setup on creating one |
| Timing | Routine frequency, broader interval/alignment, day/time/timezone | Reuse existing job; observation is not user preference; schedule and notifications need separate host configuration |
| Notifications | Quiet unchanged runs versus regular reports; deferred/revisit timing | Suppress repeated unanswered questions; one pending question, no repeated weekly interrogation |
| Search windows | Initial look-back, overlap and missed-run recovery | Per-source watermarks advance only on success; explain recommended windows before confirmation |
| Publication | Authority, library/collection, export targets/options/timing/side effects | Preserve confirmed destinations, inspect existing exports, avoid competing stores |
| Attachments | Now/later/none, public use, folder route, optional original retention and replacement/session association | Mandatory privacy flow; never overwrite; don't invent per-session material fields |
| Owner handoff | Who generates/reviews/commits/publishes and verified commands | Inspect commands and current outputs; save is not render or deployment |

A project is a user-useful body of work; no fixed taxonomy required. Sources can suggest missing projects/mentees but relationships require confirmation. A paper/grant may conceptually belong to several projects or none; current schemas may not represent that. One teaching activity can span sessions, while different decks per session and one abstract at multiple meetings need reviewed compatible representations. Hold unsupported changes, not the entire setup.

## Technical work, not compulsory questions
Inspect runtime paths, actual permissions, schemas/consumers, source/output folders, existing jobs and export settings. Ask only if inspection leaves a material choice. Mandatory approval/privacy rules are not opt-out preferences. Portable storage implementation, template delivery, schema migrations, conflict handling, stable issue identities and scheduler adapters are product work, not questions users must solve.

## Supported initialization and remaining limits
Use [initialization](initialization.md) for private CV extraction/coverage review and prototype starter delivery, followed by [reviewed execution](setup-execution.md) when selected and authorized. The bundled starter deliberately contains empty YAML; this is distinct from creating empty files to bypass compatibility checks on an existing project. Actual record imports still require exact review/approval. Automatic factual CV import, arbitrary template conversion and automatic permission grants are unsupported. Preserve source material and existing working projects. Template provenance and new-user visual Word acceptance remain pending review requirements; do not claim finished layout certification.

## Setup summary and continuity
Show what is confirmed, observed, pending and unsupported separately. Save provenance/date and unknown keys. Requests to change a preference authorize that preference change, not record writes, new sources or publishing. Continue the active review queue after a save; don't lose the next question. A disappearing or unusable structured prompt falls back to a single chat question.

For notification setup, explicitly offer a regular reminder to submit missed activities to the assistant even if automated searches find nothing, versus quiet-on-no-findings. For the chosen reminder mode, show verified CV/site links and a linked category checklist following check-in.md. Record Nothing to add versus ignored without treating either as a factual all-records confirmation. Users may inspect YAML on demand at any cadence.

For output assistance, save separate website-render, private-CV-generation, verification, commit and push/publication modes with any explicit authorization evidence under output_execution. Each may remain owner-managed. Follow output-execution.md; do not confuse preference with actual permission. Ask about these only when relevant and reuse established manual arrangements. Private CV and public CV are separate scopes; defer public-CV setup if the user chooses later.
