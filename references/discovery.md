# Discovery sources and reports

Apply [user-approved candidate exclusions](discovery-exclusions.md) after evidence-based triage and before presenting suggestions. Read current discovery.exclusions, preserve exact user scope, report counts, and retain uncertain classifications privately. A single rejected candidate is not a global rule; exclusions do not delete records or change source-search coverage.

## PubMed
Follow [PubMed access and identity](pubmed-discovery.md) before the first call: check the selected tool and actual host restrictions, use the normal scoped access flow when needed, and distinguish connectivity from completed coverage. Read identity.full_name and confirmed search_names, identifiers, affiliations and topics from the private profile. Blank optional clues alone do not trigger questions. Ask only for the smallest missing clue needed for a usable author search or consequential identity ambiguity; honor confirmations and deferrals. Do not hard-code an author or accept surname-only matches.

Compare PMID, DOI and normalized title with the main BibTeX export and accessible records from the configured publication store. Check both publication dates and recently entered/indexed records; a publication-date-only filter misses delayed indexing. Use overlap across runs. Read NCBI PubMed records and publisher metadata where needed. Distinguish ahead-of-print, final publication and corrections from new works. Report proposed additions or metadata corrections for the publication store confirmed in the profile; do not mutate that store or exports through discovery. For Zotero, hand candidates to the separate update-zotero-records workflow after review. Local connector imports support additions; existing-item corrections remain pending unless a verified editing-capable connection exists.

## Academic activities in email
Follow [email coverage and query planning](email-discovery.md) and the versioned [Gmail query catalogue](email-queries.json). Use only saved authorized accounts/categories. Prepare exact definitions with scripts/email_queries.py; do not improvise subject-only groups or silently share a narrow scope's cutoff with broader searches. New or expanded scopes require the applicable authorization and their own saved initial look-back. Preserve old checkpoints as evidence. Complete every declared subquery and page before advancing that scope; incomplete searches retain the old cutoff. Disclose selected account, categories, window, omitted categories and keyword limits in the user-facing check-in, not just private logs.

Read matching threads and relevant attachments only as needed. Acceptance does not prove presentation. Verify title, author order, meeting, date, location and presentation type against official program or user confirmation. Do not send, draft, label, archive or modify mail. Report minimal evidence with a source link; no sensitive email text in public files.

## Media online
Search the full name with interview, podcast, quoted, news and relevant topics. Prefer original publisher pages. Distinguish authored writing, interviews and quotes; check identity and original publication date. Use the approved media destination in the profile if present. If none is configured, report candidates without inventing a destination or creating files. A destination outside the supported YAML adapter remains report-only.

## Accessible chats
Use the current conversation and authorized history/search tools actually exposed by the host. Do not imply automatic access to every ChatGPT conversation, project or memory. Dated direct user statements are stronger than speculative plans or assistant-generated drafts. A chat mention is a candidate unless the user clearly reported a completed activity. Include only a brief relevant reference; never copy private chat transcripts to public records.

## Configured runs
Read enabled sources and initial/overlap windows from discovery settings; read routine cadence, day/time/timezone, notification rule and automation identity from canonical review settings. Reconcile conflicting legacy mirrors before relying on them. No packaged frequency or source is an answer. If settings are incomplete, ask only what is needed or clearly label a one-off suggested search window. Scheduler configuration is separate from this package. Use the profile's initial window until a verified prior successful run exists, then its overlap window. Do not advance a failed source's last-success marker. Never claim a saved watermark if there is no authorized persistent run-state location. Compare accessible previous reports to avoid repeated alerts; if unavailable, disclose possible repeats. Store private state only outside the repository with authorization.

Each actionable candidate: activity type; proposed title/date; identity evidence; source link and retrieval date; matching existing record/key; what changed; confidence and unanswered questions; eligible YAML destination or outside-scope destination. Include search window and coverage gaps. Follow the user's confirmed notification rule; until configured, provide the explicitly requested report and do not create a schedule. Never claim a search was run when only setup was completed.


For approved media.yml destinations, follow [media records](media.md). Check existing item URLs and embed sources for duplicates, preserve coverage-versus-appearance wording, and obtain approval of every exact record proposal. Missing destination/schema permission leaves candidates pending.

For current installed plugin resolution and existing scheduler/profile reconciliation, follow [scheduling](scheduling.md). Use the [conditional questionnaire](questionnaire.md) for missing setup; recurring chat review requires a separately confirmed chat scope.

## Incremental search windows and per-source checkpoints
The initial look-back is resolved at the first actual discovery search if not already confirmed, then saved; do not ask every week. Subsequent runs start from each source's last successfully covered cutoff minus the saved overlap interval. A two-week overlap is a useful recommendation; retain the user's confirmed interval and permit changes by request.

Define the source key by provider plus account/calendar/library/project identity and the search-scope/query version. Different accounts or materially changed query scopes cannot share an unexamined checkpoint. A new source without a usable checkpoint uses the confirmed initial-window policy; if that choice remains unknown, ask one necessary question and hold only dependent searches.

Capture an explicit inclusive search window in UTC with original timezone/date-only API interpretation recorded. Use a fixed upper cutoff captured before the search, not the later completion time. For a valid checkpoint, start = last_successful_cutoff - overlap_days; end = current run's fixed cutoff. Retain previous coverage bounds. With no checkpoint, ask/use initial look-back at first search. Never advance a cutoff into a future/unsearched interval.
Record query scope, provider/account key, window bounds, run ID, completion time, actual coverage/pagination, evidence/report reference, and outcome in private reviews/discovery-checkpoints.json or the configured equivalent. Save with the profile's atomic-write/backups/concurrency safeguards. Do not store raw correspondence or identifiers unrelated to source selection. Missing state does not prove a search ran, and no successful checkpoint is created by setup alone.

Advance only that source's last_successful_cutoff after its complete intended window was actually searched, all required pages/subqueries were covered and results/candidates were durably saved. A successful zero-result search may advance. Failed, interrupted, unauthorized, unavailable, rate-limited or partial searches retain the prior successful cutoff and separately record the failed attempt. Save/report failure also retains the old cutoff. Other successfully completed sources may advance independently. This automatically catches up after missed/failed weekly runs without the user picking a fresh look-back.

Successful checkpoint commits also retire the exact recognized first-search placeholder note under private-state.md; unknown notes and historical before-copies remain intact. Do not manually delete or rewrite legacy state to make a report look current. Source run/cutoff evidence governs search coverage. Output verification is separate: recheck CV/site evidence under cv-output.md, retain dated observations and leave inaccessible, cached or otherwise unverified outputs honestly unverified rather than backfilling a claim.

Use the packaged [private-state helper](private-state.md), not an ad-hoc checkpoint writer. Call checkpoint-begin before searching to capture the source/account/query identity, cycle, fixed UTC bounds, confirmed initial/overlap window and intended subqueries. Complete only with exact returned bounds, exhausted pagination for every declared subquery and durable nonempty report/result files; the helper checks assertions, hashes and current profile before its atomic commit. It cannot prove remote search completeness. Use checkpoint-fail for partial/failed/unavailable work, retaining the last successful cutoff. A command interrupted after replacement may already have committed its cutoff: inspect operation status and use receipt-only verify, never advance again blindly. If the helper cannot run or persist state, report the save pending and retain the prior checkpoint; do not invent completion or bypass its checks.

Deduplicate repeated retrieval against authoritative records and private prior findings using source-native IDs, DOI/PMID and appropriate normalized title/activity matching. Preserve evidence and materially changed facts/status as updates to an existing candidate, not a dropped duplicate or a second activity. Overlap is not evidence that a candidate is new. Delayed indexing should use source ingestion/update-date queries where supported; a finite overlap cannot guarantee all indefinitely delayed records, so disclose source limitations rather than claim completeness.

## Existing publication export continuity
Reuse the saved publication export setup during weekly review. Compare accessible relevant export status and bibliography coverage with prior evidence; raise meaningful failures or changed scope/targets rather than reopening the export questionnaire each week. If export evidence is stale or incomplete, do not treat absence from that file as proof of absence from Zotero: check the accessible target library or label duplicate coverage incomplete. Report export concerns separately from discovery results. Discovery never imports, refreshes/reconfigures exports or writes bibliographies; approved additions use update-zotero-records and its separate import/export verification.
