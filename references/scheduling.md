# Scheduler and current plugin binding

Schedules are host-managed, separate from installation and preference files. Before creating or changing one, discover existing jobs using supported host APIs/configuration. Match by project, workflow and known identity; preserve IDs and avoid duplicates. A saved profile with a null automation ID is not proof no job exists. Reconcile documented legacy job/profile references first.

The scheduler prompt should identify CV and Website Maintainer (academic-records) by stable plugin identity/name and resolve its current installed release at run time. Never copy an old workflow or version-specific cache path into the prompt. Read the installed manifest and record executed version and any available release identity in the private run receipt. If authorized metadata tools can check the saved current release, compare it with the installed release. Do not claim latest-release verification without evidence. If the installed package is known stale, missing or below the configured minimum compatible version, report setup/update required once and leave dependent review work pending; do not install/update packages unattended or fall back to a frozen older workflow. If latest-release metadata is unavailable, distinguish current-installed execution from unverified latest availability.

Keep the profile as the canonical settings store and the scheduler as the executor. review.* owns routine cadence, broader interval, anchor, timing, notification preference and automation identity. discovery.* owns sources, identity-related query settings and initial/overlap windows; legacy timing mirrors must be synchronized during migration, not silently selected when conflicting. Observed scheduler timing belongs in a separate observation, not a confirmed preference.

A configured schedule is not evidence the review ran successfully. Preserve existing status, timing, target and notification policy unless the user authorizes a change. Updating an existing job to the current plugin/profile does not authorize a new delivery time or account scope. Keep timing questions pending when the observed time was assistant-selected. Disabled/paused jobs stay paused unless activation is authorized.

Broader reviews aligned to every N routine cycles need a confirmed anchor. Do not backdate completion, invent a cycle count or count failed searches as successful reviews. Use due dates independent of per-source search success, and retain one pending broader review if unanswered. Record success/checks/source gaps, not just scheduler dispatch.

## Routine read-only scheduler inspection

During routine maintenance, first read the CURRENT local task configuration when this host exposes it and access is authorized. On local Codex, use the known job ID/profile/task locator to read its automation.toml; do not scan unrelated task folders or hard-code a packaged user's job. Parse the file as configuration data, validate the job identity and actual destination, and compare saved prompt/binding, recurrence, status and exposed notification fields with current profile preferences. Record the observation time and content hash privately. A recent prior verification is not a substitute for a fresh read on this run. A matching file only establishes the stored local configuration, not that the scheduler ran or the host is using every setting as intended.

When a fresh, valid, matching local file establishes the fields needed for an ordinary check, avoid a redundant automation_update mode=view call. Use the native host view when the file is missing, unreadable or malformed, its identity/destination is wrong or ambiguous, observations conflict, or verification needs host-only fields. Also honor an explicit user request for a live host check. Do not infer a timezone, next run, DST result, notification delivery or execution success from fields the file does not expose. Keep those items unverified unless supported host evidence settles them. A host view that also lacks them does not settle them either.

After creating or updating a task, retain the native host read-back in the setup procedure below; the routine file-first shortcut does not replace post-mutation verification. Never edit task files directly to avoid a host tool. Preserve timing/status/destination and require the existing authorization for changes. If file/host access is unavailable, report scheduler verification incomplete and continue independently permitted local checks instead of treating missing metadata as a configured or successful schedule.

Measure delay honestly: call start-to-completion elapsed time may include host waiting, queuing or approval handling, while a reported execution duration can measure something narrower. Keep both when available; do not attribute all elapsed time to tool computation or promise a fixed speedup. These instructions reduce redundant calls, not scheduler latency guarantees. They do not change any existing job, preference, permission or route.

## Configure the actual host task during setup
Schedule creation/update is a supported part of the preference-setup workflow and must also be called during initialization when scheduled reviews are requested. Do not stop after merely saving the chosen frequency. Installation alone still creates no task.

1. Discover the host's supported scheduler and existing relevant tasks. In Codex use automation_update and inspect existing automation configuration when needed; prefer the current-chat heartbeat for recurring follow-ups unless the user explicitly requests standalone tasks. Other hosts require their verified native scheduler adapter. In Claude, scheduled reviews are not set up yet: reviews run when the person asks, no Claude task is created, and automation_id is left as it is. Never store a Claude task ID in automation_id; say plainly that scheduling is unavailable in Claude and continue the rest of preference setup. Do not simulate a scheduler through shell cron/jobs or create a separate chat without authorization.
2. Load the canonical profile, confirmed sources/cadence and actual host access. Collect unresolved day, time, timezone, notification behavior, execution destination and broader-review anchor one question at a time. Inspect destination/access instead of asking users to repeat discoverable details. Confirm that the host timezone matches the requested timezone; a timezone string in a prompt does not configure scheduler timezone. If the host cannot express the requested specifications, explain that limitation.
3. Assemble a concise concrete schedule summary: cadence and local time/timezone, execution chat/project, included review scope, broader interval/anchor, notification behavior and exact private profile. If the user has already explicitly authorized this specified schedule, proceed; otherwise ask one activation/summary confirmation. No redundant permission question for an already approved specification. A new-frequency preference by itself is not consent to activate a previously disabled schedule.
4. Build a human-readable prompt invoking current installed CV and Website Maintainer (academic-records) by stable identity and canonical profile, with the version/freshness checks above. Include source restrictions, approval-only record changes, broad-cycle behavior and the confirmed notification/reminder intent; quiet unchanged runs apply only when chosen. Keep private credentials and source excerpts out of the prompt. Use actual profile values; no packaged person's defaults.
5. Call the native scheduler create or update tool. Reuse an existing job's identity. For updates preserve fields the user did not change, including status, destination and notification policy. A new job is created only when none matches and activation is authorized.
6. Read back the saved job and verify ID, prompt, cadence, timezone interpretation, destination, status and notification behavior against the approved specification. If timing precision/timezone cannot be verified, mark verification incomplete, not fully configured. Save the task ID, verified configuration, confirmation provenance and observed next run when exposed into private review settings; synchronize legacy mirrors. A successful task creation without a saved profile link is a partially configured task: keep its ID and reconcile, never blindly create another.
7. Report actual state: configured and active, configured and paused, or pending with the exact missing capability/answer. Keep setup resumable. Later requests to change frequency run this same update-and-verify path for the existing task rather than changing config alone.

If the host has no usable scheduler or scheduled environment cannot access the required profile/sources, save preferences as pending and offer an explicitly authorized handoff to a capable host. Never claim that instructions alone will run every week. Do not require the full site/CV initializer to finish before configuring an otherwise ready maintenance task.

## Check-in content in created tasks
When setup creates or updates review tasks, include [check-in.md](check-in.md)'s sequence in the task prompt: suggested updates from authorized discovery first; existing CV/website links with honest freshness; linked category checklist; assistant-guided submission; Nothing to add and no repeated same-cycle nudges. A user choosing weekly submission reminders receives that message even with no automated findings. Make notification policy consistent: a failures-only mute can suppress successful check-ins, so apply the user's explicit changed reminder preference through the host notification controls and verify it. Do not tell users to edit outputs themselves. Native file-panel/checklist controls depend on the host; preserve a working chat/link fallback. The broader sweep interval is independent of on-demand record viewing.

## Incremental discovery in every configured task
Tasks created/updated by setup must use discovery.md's per-source successful-cutoff rule: only the first search needs the initial window; later searches cover last successful cutoff minus the saved overlap through a fixed current cutoff, deduplicate results, and preserve failed/partial sources' previous checkpoints. Checkpoints are source/account/scope specific, persisted privately only after complete coverage and saved results. Do not prompt for a new look-back every week or advance checkpoints merely because the scheduler fired.

## Saved output assistance in tasks
Created tasks must load [output-execution](output-execution.md) and the same per-stage output preferences as interactive maintenance. Default or owner-managed modes remain instructions-only. Explicitly authorized generation/verification/commit/push stages may follow a verified approved save only within their actual tools/path/repository authorization; discovery candidates and reminders do not themselves authorize a save or output run. Per-run approval modes pause at their checkpoint. Standing execution is conditional on explicit scope evidence, not a preference label. Public CV preparation/publication remains a separate opt-in workflow and may be deferred.

## Runtime progress in configured tasks
Created/updated task prompts use check-in-status/check-in-record from private-state.md for cycle dispatch, selection/closeout and broader-review progress in the separate private file. config.json remains preference authority. Existing prompts that load current installed instructions can follow this storage change without editing the live task. Do not invent historical dispatch, infer closure from silence or change schedules. Follow inspected interrupted-run checkpoint-fail guidance; never advance incomplete coverage or steal unknown workers' locks.


## Local availability

For local-file reviews, keep the computer on, the desktop app running and the project/profile accessible. See [official scheduled-task guidance](https://learn.chatgpt.com/docs/automations). Do not promise automatic replay of missed triggers. Inspect run status and retain source checkpoints on failure; a later successful search uses the saved last-successful cutoff plus overlap, which can recover coverage without fabricating a missed run. See the [installation guide](installation.md). This guidance does not alter any existing task.
