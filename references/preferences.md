# Private preferences and resumable setup

## Locate before creating
At each workflow start, read authorized project instructions/session locators. In local Codex check only the documented USER_HOME/.codex/academic-records/profiles.json registry and handoff.json full_profile_locator when available. In Claude Code on the same computer, check the same documented files: the folder keeps its Codex name for compatibility, and the same registry serves people who use only Claude. Never create a second registry under ~/.claude, so someone who switches between Codex and Claude keeps one profile. Match exact project roots, never the most recent profile. Also inspect known job/profile references supplied by context or existing academic automation configuration through supported tools. Do not scan unrelated private folders.

If more than one real profile or conflicting locator/job exists, reconcile before creating defaults or overwriting. Preserve copies, dated decisions, pending items, receipts, unknown keys, consumer maps, export observations and ongoing design-plan pointers. A new path does not establish a new authority. Resolve retirement markers to canonical_profile_path before invoking helpers; do not apply writes using retired profiles. Ambiguous conflicting user choices require one focused question; newer explicit confirmations can supersede older choices with provenance. Environment observations are not personal preferences.

Distinguish missing, malformed and inaccessible profiles. A genuinely missing profile triggers guided setup; inaccessible/corrupt existing state requires access or reviewed recovery, not silent replacement. Propose a project-specific private state directory outside the public repository and plugin, confirm it when not already authorized, and verify actual access with a unique removable probe or actual verified authorized creation. Use host escalation as required.

## Progressive setup
Follow questionnaire.md and questions.md. Prefill known confirmations and inspect discoverable facts. Save each actual response as a pending answer before the next question; do not create or edit config.json after every answer. Use the pending-answer procedure below. Unknowns stay pending; never populate example defaults as user choices. Readiness is per capability; missing scheduling answers must not block a supported local record update. If persistence is unavailable, state session-only limits and offer authorized handoff. Never use public YAML as a settings fallback.

### Pending answers, then one profile proposal
For a new initializer, use initialize.py answer for its supported seven bootstrap keys; initialization.json is interview state, not preference authority. Do not extend that helper's accepted keys ad hoc or restart initialization for an existing profile.

For supplementary questionnaire answers, or configuration of an existing profile, use an explicitly authorized private STATE/setup-answers/ directory outside the public project, plugin and Git checkout. This is an agent procedure, not a packaged answer-staging helper: save each response as a new exclusively created UUID.json file, UTF-8, with question_id, question_text, value, actual_response, response_reference, recorded_at, disposition (answered/deferred) and supersedes (prior answer ID or null). Keep unknown response-message times unknown; recorded_at is the actual save time. Do not overwrite a previous answer, store secrets/raw correspondence or manufacture a confirmation. Verify the saved bytes/parsed contents and report the path. Check actual boundaries, existing-profile project_root when present and host permissions before writing; malformed/inaccessible profiles require reviewed recovery. An approved storage location does not approve preference application. Reuse initialization.json plus these pending answers on resume; conflicts need one focused question. Do not put pending answers into public YAML or a competing config file.

At a natural questionnaire checkpoint or the user's pause, combine only the confirmed answers into one merge patch and dated provenance linking the exact answer IDs/references. Map answers to the actual supported profile schema; deferrals stay pending and must not become enabled capabilities. For an existing profile preserve unrelated/unknown keys. For first creation wait until the actual project directory exists and its boundary is known; a planned project_path is not enough. Then use private_state.py profile-propose (with --create only for genuine first creation), show the exact combined before/after and ask one approval question. Apply only that exact approved proposal with actual approval evidence. A factual answer is not approval of an unseen combined profile. If the candidate changes, prepare a fresh proposal and get approval again. No per-answer profile-apply calls are required merely to continue interviewing.

After verified profile application, retain the original answer files and add a separate immutable reconciliation note linking the applied proposal/receipt and included answer IDs; leave excluded/deferred answers pending. Do not silently mark them all completed or delete interview history. If project creation or approval is not ready, report preferences pending and resume later without an incomplete config.json. Native task, route, source access, installation and publication authorization remain separate; saving pending answers grants none of them.

Use config.json for preferences; pending/ and events/ for questions/dispositions; proposals/ for exact changes/receipts; reviews/ for coverage, watermarks and review history. If the user maintains ongoing design work, reuse their optional development_plan_path and linked design_records before relevant plugin/initializer changes. Ordinary setup and records maintenance do not require a development plan, and no plan is created automatically. These are planning references, not new write authorization.

Before updating an existing file, read/hash it, create a unique hash-verified backup, preserve unknown keys, recheck the hash, write through a temporary sibling and atomic replacement, then verify parsed content. Initial creation is exclusive. Refuse concurrent changes. Preserve immutable historical receipts rather than rewriting their paths; store legacy_state_roots and index what remains there. Document migration receipts and canonical/retired locations so later chats do not rediscover the same conflict. No encryption or cross-computer sync is bundled.

For profile creation/changes, use the packaged [private-state helper](private-state.md): profile-propose shows exact before/after and dated provenance; profile-apply requires approval of that proposal and a reference to the actual response. It preserves unspecified keys, checks stale state, serializes cooperating writers and saves verified backups/receipts. Use its status/verify path after interruptions; never blindly repeat a write or silently fall back to ad-hoc JSON edits. The helper does not validate every preference's meaning, grant access or modify a native task/route. If another private state file lacks an applicable helper, describe its safeguards as agent procedure rather than claiming executable enforcement. No plugin update itself authorizes a live profile edit.

## Preference and scheduler ownership

For the narrow case of a single preference choice with an already displayed exact validated proposal, follow questions.md: an explicitly labelled approval of its named proposal can also supply the choice. A bare questionnaire answer cannot approve unseen bytes. Preserve actual response evidence and pending answers as applicable; this exception does not replace combined questionnaire checkpoints or authorize per-answer profile edits throughout setup.
A direct request changes that stated preference; record old/new/date/source and clarify only ambiguity. It never approves record edits or expands access. review.* is canonical for routine timing, broader interval and notifications/job identity. discovery.* holds sources and search windows. Keep legacy schedule mirrors consistent; conflicting values require reconciliation. See scheduling.md for discovering existing jobs and current installed plugin binding.

Support portable conceptual preferences and separate machine-specific paths/runtime/route observations. Moving to another host requires verified storage and permission setup or an explicit profile transfer; plugin installation does not transfer settings. Do not silently merge multiple computers' concurrent histories or create a second scheduler. Optional backup/retention/transfer preferences can be resolved when relevant.

Source selections are account/calendar/chat scoped and must be confirmed before searching. Reuse approved source types but resolve missing specific account scope rather than presume all connected accounts. Report unavailable/failed/unauthorized coverage. Keep credentials and raw correspondence out of settings.

Save dated confirmations, rejected/deferred candidates, evidence references and revisit triggers. Reopen dismissed items only for meaningful new evidence or agreed dates. Continue the next pending question after a completed save when the user is conducting a review, respecting pauses and deferrals.

Routine progress is not a preference answer: record actual check-in dispatch, selection/closeout and broader completion through [runtime commands](private-state.md#routine-check-in-progress), never profile-apply or ad-hoc config edits. Keep current freshness in private evidence reports; retain saved preferences and dated observations.
