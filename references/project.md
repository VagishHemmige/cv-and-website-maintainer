# Project adapter and user profile

The reusable plugin contains workflows and an adapter for the existing 13-file academic website schema. User identity, project paths, approved write scope, source selection, schedule and maintenance preferences belong in a private profile, never in this package. Read [setup](setup.md) before use.

Find the profile from a user-provided location, authorized project instructions or previously available session context. If no locator is available, ask where the existing profile is before making a new one. Do not scan arbitrary private directories. Installation does not provide access or persistent memory. Read the profile's data_root and project_root, then the actual applicable AGENTS.md and relevant consumers. Reconcile existing confirmations and questions; do not redo import or ask answered questions.

Required schema adapter files: abstracts.yml, appointments.yml, certifications.yml, education.yml, grants.yml, honors.yml, memberships.yml, mentoring.yml, projects.yml, service.yml, talks.yml, teaching.yml, training.yml. Optional media.yml is supported when already present; see [media records](media.md). These are capabilities, not granted write permissions. The approved_files profile list is the user-approved subset; the helper must refuse anything outside it. A different schema needs a reviewed adapter, not an inferred expansion. The validator currently needs all 13 required files present (media.yml remains optional), even when only a subset is writable; disclose that limitation during setup.

All files use sequences of mappings. Abstract types oral/poster; scope international/national/regional/local. Talk categories invited/conference/grand_rounds/teaching. Mentoring status Active/Former. Project status active/completed/paused. Preserve scalar/list/null distinctions, case-sensitive resource paths and date precision. Abstract authors and talk role stay scalar; teaching dates remain a list. Do not invent full-date precision to satisfy a consumer.

Inspect and record the actual consumer map in the private profile. Known adapter conventions include abstract anchors from title/meeting/year, exact mentee names, project-title references and BibTeX manuscript keys. Verify against actual source. The bibliography_file profile answer names the optional read-only bibliography in the data folder. The helper passes that name to the validator; direct validator calls accept an optional second BIBLIOGRAPHY_PATH argument. Without a configured bibliography, disclose incomplete manuscript-reference checks. Never edit the bibliography or create a competing publication authority.

Routine YAML updater scope: approved YAML only. The separately invoked update-zotero-records workflow can add user-approved records to the configured Zotero library through an available companion Zotero integration. It does not grant bibliography export, attachment, consumer, render, Git or publishing permissions. No CV/site output generation, parent source edits, Git mutations, publishing or email mutations. The optional [attachment workflow](attachments.md) separately supports approved PDFs in explicitly authorized resource folders, with mandatory [privacy warnings](privacy.md); resource placement does not expand the YAML allowlist or authorize other parent writes. Ask which publication store and media destinations are authoritative instead of assuming Zotero or a missing media schema. Record those answers. Respect explicit project restrictions and host permissions. Read no private contact files unless specifically needed and authorized.

Questions should resolve actual uncertainty: current role, planned appointment outcome, institution, date precision, same work at multiple meetings, award attribution or complete authors. Reuse dated answers from the profile and authorized project context. Never assume an event occurred because its planned date passed.


For documented profile locators, missing-file initialization and preference changes, follow [preferences](preferences.md). Do not silently create a competing profile when an existing one is inaccessible.

If the user has configured development_plan_path or design_records, consult those existing references for requested design/plugin work. They are optional development context, not prerequisites for ordinary records maintenance; do not create a development plan for every user. Respect retired-profile canonical redirects and known existing automation/profile references before creating a new profile. See [questionnaire](questionnaire.md) and [scheduling](scheduling.md).

## Explicit bibliography scope
The proposal helper passes an explicit bibliography path when configured, or --no-bibliography when the profile setting is null/absent. Null consistently keeps manuscript-reference checks incomplete with a visible warning, even if publications.bib exists or appears later. This preserves the reviewed source scope and avoids silently reading an unconfigured export only after saving. Configure the intended bibliography through a separately reviewed preference change to enable key checks. Standalone validate.R with only DATA_DIRECTORY retains its publications.bib default; its optional --no-bibliography argument explicitly disables that fallback. No profile, export or historical proposal/receipt is migrated by this fix. Older already-saved proposals retain their original reviewed diagnostics; any mismatch still needs reconciliation, not automatic rewriting.
